# NailGo — маркетплейс мастеров маникюра

Клиентское приложение (поиск мастера и запись) и кабинет мастера. Фронтенд живёт
в корне репозитория, API — в `apps/api`.

| Часть | Стек | Где |
| --- | --- | --- |
| Клиент + кабинет | React 19, Vite, Tailwind, react-router | `src/` |
| API | Fastify, Drizzle ORM, Zod, JWT | `apps/api/` |
| БД локально | PGlite (Postgres в WASM, файл в `apps/api/.pglite`) | `DATABASE_URL="pglite://./.pglite"` |
| БД на сервере | PostgreSQL | `DATABASE_URL="postgresql://…"` |

## Быстрый старт

```bash
# 1. Фронтенд
npm install
npm run dev                     # http://localhost:5173

# 2. API
cd apps/api
cp .env.example .env
npm install
npm run db:migrate              # применить миграции
npm run db:seed                 # демо-данные (мастера, услуги, записи недели 20–26 мая)
npm run start                   # http://127.0.0.1:4000/api/health
```

Локально используется PGlite — это один процесс на каталог `apps/api/.pglite`, поэтому
сиды накатываются **при остановленном API** (скрипт сам скажет, если база занята).
Если база заклинила после аварийного завершения, есть жёсткий сброс:

```bash
cd apps/api
npm run db:wipe                 # удалить каталог данных, накатить миграции и сиды заново
```

В dev-режиме Vite проксирует `/api` на API, поэтому браузер никогда не обращается
к `localhost` напрямую — это важно для окна предпросмотра и для прода.
Адрес API переопределяется переменной `VITE_API_TARGET`, публичный адрес — `VITE_API_URL`.

## Что уже работает

- каталог мастеров и услуг берётся из API (если API недоступен — показывается демо-каталог);
- вход по телефону: `POST /api/auth/request-otp` → код, `POST /api/auth/verify-otp` → токен.
  Куда уходит код, решает `OTP_DELIVERY`: `response` — в ответе API (локально),
  `log` — в лог сервера (закрытый стенд), `sms` — через провайдера (ещё не подключён,
  API честно ответит `503 sms_not_configured`);
- клиент записывается: свободные окна считает сервер, двойная запись на одно время
  невозможна (HTTP 409 `slot_taken`);
- клиент видит и отменяет свои записи (`/account`); записи отдаются по токену сессии,
  номер телефона в запросе не даёт доступа к чужим данным;
- кабинет мастера (`/pro`) закрыт ролью `master`: гость уезжает на вход, клиент видит
  «кабинет доступен мастерам». Кабинет читает те же записи из БД (расписание, таблица
  записей, клиенты, статистика за месяц) и создаёт записи, которые сразу видны клиенту;
- мастер меняет статусы записей прямо из таблицы «Записи»: «Подтвердить», «Завершить»,
  «Отменить» и карточка «Детали записи». Изменения сразу видны клиенту в его кабинете;
- уведомления в приложении: клиент, оставивший заявку, появляется у мастера (колокольчик
  со счётчиком непрочитанных в кабинете), мастер подтверждает и завершает визит — клиент
  видит это в ленте `/notifications`. События хранятся в таблице `notifications`,
  `GET /api/notifications` отдаёт ленту, `POST /api/notifications/read` отмечает прочитанное
  (клиент — по телефону из токена, мастер — по своему аккаунту). Это не SMS и не push:
  уведомления живут внутри приложения;
- «Отзывы» работают на данных базы: мастер видит свои отзывы с оценками и статусами
  (опубликован / на модерации / скрыт) и меняет статус прямо из списка; клиентская витрина
  `/reviews` показывает только опубликованные отзывы через публичный `GET /api/reviews`;
- «Статистика», «Клиенты», «Продвижение» и главная кабинета считают цифры по базе:
  выручка, средний чек, топ услуг, статусы, источники записей, динамика по дням и база
  клиентов с визитами и чеками. Рекламных метрик (показы, клики, расходы) в системе нет —
  такие блоки помечены на экране как демонстрационные до подключения рекламных кабинетов;
- таблица «Записи» показывает реальные данные из базы (строки макета остаются только
  как запасной вариант, если API недоступен), счётчики вкладок считаются по этим же данным;
- переписка клиента с мастером живёт в базе (`/messages`): диалог заводится с карточки мастера
  или из кабинета, сообщение второй стороне приходит в ленту уведомлений, непрочитанные считаются
  по собеседнику и видны значком в кабинете; внешних каналов (SMS/WhatsApp/Instagram) нет;
- статистика кабинета считается по записям: воронка «записи → подтверждённые → завершённые»,
  динамика за 12 месяцев, топ услуг, источники записей — без демо-чисел;
- настройки сохраняются в базу: профиль (`PATCH /api/cabinet/profile`) и часы работы
  (`PUT /api/cabinet/hours`). Выходной день закрывает запись: клиент не видит окон,
  а попытка записаться получает 409 `day_off`;
- сессия не обрывается: access-токен живёт 15 минут, refresh — месяц.
  `POST /api/auth/refresh` продлевает пару с ротацией (старый refresh перестаёт работать),
  сессии хранятся по устройству (`sessions`), `POST /api/auth/logout` отзывает свою сессию,
  а клиент сам продлевает доступ при первом 401 — пользователь не вводит код заново;
- демо-данные пересоздаются из кабинета: `POST /api/cabinet/demo/reset` (только dev).

## Демо-доступы

| Роль | Телефон | Что видно |
| --- | --- | --- |
| Мастер (владелица кабинета) | `+7 999 000-00-01` | кабинет `/pro` целиком |
| Клиент | любой новый номер | запись, «Мой профиль», отмена |

Код подтверждения в dev-режиме возвращает сам API (`OTP_DELIVERY=response`, он же
по умолчанию при `DEV_OTP_ENABLED=true`) и подставляется в форму автоматически —
SMS не нужны, пока не подключён провайдер. На стенде без провайдера включайте
`OTP_DELIVERY=log` и смотрите код в логе API.

## Проверки

```bash
npx tsc --noEmit                  # типы фронтенда
npm run build                     # сборка фронтенда
cd apps/api && npm run build      # типы и сборка API

# сквозные проверки без браузера (нужен запущенный Vite + API)
cd tools/devcheck && npm install
npm run bundle                    # собрать приложение в bundle.js
npm run routes                    # отрисовать все маршруты (кабинет — под сессией мастера)
npm run e2e                       # сценарий «мастер создаёт запись → завершает → клиент видит и отменяет»
npm run data                      # цифры разделов и витрины совпадают с ответами API
npm run messages                  # переписка: диалоги, непрочитанные, отправка в обе стороны
npm run stats                     # воронка и динамика из базы, сохранение профиля и часов работы
npm run session                   # продление сессии, ротация refresh, выход и автопродление в клиенте
```

## Переменные окружения

- фронтенд: `VITE_API_URL`, `VITE_API_TARGET`, `VITE_ALLOWED_HOSTS`;
- API: см. `apps/api/.env.example` (порт, секреты JWT, TTL кода, шаг слотов, рабочие часы).

Прод собирается как три контейнера — сайт (`Dockerfile.web`: сборка Vite + Caddy),
API (`apps/api/Dockerfile`) и Postgres; серверный образ работает на драйвере `pg`,
локальный WASM-драйвер PGlite в него не попадает. Миграции API накатывает при старте,
так что отдельного шага с миграциями в деплое нет. Подробности — в [DEPLOY.md](./DEPLOY.md).
