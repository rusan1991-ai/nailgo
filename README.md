# NailGo — маркетплейс мастеров маникюра

Клиентское приложение (поиск мастера и запись) и кабинет мастера. Фронтенд живёт
в корне репозитория, API — в `apps/api`.

| Часть | Стек | Где |
| --- | --- | --- |
| Клиент + кабинет | React 19, Vite, Tailwind, react-router | `src/` |
| API | Fastify, Drizzle ORM, Zod, JWT | `apps/api/` |
| БД локально | PGlite (Postgres в WASM, файл в `apps/api/.pglite`) | `DATABASE_URL="pglite://./.pglite"` |
| БД на сервере | PostgreSQL | `DATABASE_URL="postgresql://…"` |

## Быстрый старт

```bash
# 1. Фронтенд
npm install
npm run dev                     # http://localhost:5173

# 2. API
cd apps/api
cp .env.example .env
npm install
npm run db:migrate              # применить миграции
npm run db:seed                 # демо-данные (мастера, услуги, записи вокруг текущей недели)
npm run start                   # http://127.0.0.1:4000/api/health
```

Локально используется PGlite — это один процесс на каталог `apps/api/.pglite`, поэтому
сиды накатываются **при остановленном API** (скрипт сам скажет, если база занята).
Если база заклинила после аварийного завершения, есть жёсткий сброс:

```bash
cd apps/api
npm run db:wipe                 # удалить каталог данных, накатить миграции и сиды заново
```

В dev-режиме Vite проксирует `/api` на API, поэтому браузер никогда не обращается
к `localhost` напрямую — это важно для окна предпросмотра и для прода.
Адрес API переопределяется переменной `VITE_API_TARGET`, публичный адрес — `VITE_API_URL`.

## Что уже работает

- каталог мастеров и услуг берётся из API (если API недоступен — показывается демо-каталог);
- **вход без SMS и пароля.** Кнопки «в один клик» на `/login` и `/register`: Яндекс ID и VK ID
  (`POST /api/auth/oauth/:provider/start` → редирект провайдера → `/auth/callback`, токены
  приходят во фрагменте ссылки и не попадают в логи), Telegram и Max — по диплинку в бота
  (`POST /api/auth/bot/:provider/start` отдаёт одноразовую ссылку, бот подтверждает её вебхуком,
  клиент забирает сессию из `GET /api/auth/bot/:provider/status`). Пустой `CLIENT_ID` означает
  «провайдер не подключён»: кнопка выключена, ручка отвечает `503`. Телефонный код
  (`POST /api/auth/request-otp` → код, `POST /api/auth/verify-otp` → токен) остался инструментом
  стенда: в проде ручка отвечает `503 phone_login_disabled`. Один аккаунт может иметь несколько
  способов входа (`identities`), телефон — необязательный контакт в профиле;
- клиент записывается: свободные окна считает сервер, двойная запись на одно время
  невозможна (HTTP 409 `slot_taken`);
- клиент видит и отменяет свои записи (`/account`); записи отдаются по токену сессии,
  номер телефона в запросе не даёт доступа к чужим данным;
- кабинет мастера (`/pro`) закрыт ролью `master`: гость уезжает на вход, клиент видит
  «кабинет доступен мастерам». Кабинет читает те же записи из БД (расписание, таблица
  записей, клиенты, статистика за месяц) и создаёт записи, которые сразу видны клиенту;
- у каждого мастера свой прайс: `GET /api/cabinet/services` возвращает только его услуги,
  мастер создаёт, правит цену и длительность, скрывает и удаляет их
  (`POST|PATCH|DELETE /api/cabinet/services/:id`). Чужие услуги недоступны (403), услугу
  с записями удалить нельзя — API отвечает 409 `service_in_use` и предлагает скрыть её
  (`active: false`): из витрины и свободных окон она пропадает, история визитов остаётся.
  Клиент видит прайс выбранного мастера на `/booking`, в карточке мастера и на главной,
  а записаться может только на его услугу — чужая услуга получает 404 `service_not_found`;
- кабинет мастера изолирован: записи, расписание, клиенты и статистика считаются только
  по его собственным визитам — чужой клиент в чужой кабинет не попадёт;
- мастер меняет статусы записей прямо из таблицы «Записи»: «Подтвердить», «Завершить»,
  «Отменить» и карточка «Детали записи». Изменения сразу видны клиенту в его кабинете;
- запись можно перенести на другое время: клиент — из «Моего профиля» («Перенести»),
  мастер — из карточки записи в кабинете. Свободные окна считает сервер, правила те же,
  что при создании записи (рабочие часы, выходные, анти-овербукинг), плюс нельзя перенести
  чужую, отменённую или завершённую запись; вторая сторона получает уведомление,
  а статус записи не сбрасывается;
- уведомления в приложении: клиент, оставивший заявку, появляется у мастера (колокольчик
  со счётчиком непрочитанных в кабинете), мастер подтверждает и завершает визит — клиент
  видит это в ленте `/notifications`. События хранятся в таблице `notifications`,
  `GET /api/notifications` отдаёт ленту, `POST /api/notifications/read` отмечает прочитанное
  (клиент — по своему аккаунту, мастер — по своему). **Платных SMS у площадки нет:**
  наружу сообщение уходит в привязанный мессенджер (Telegram, иначе Max), а без привязки —
  в журнал системы. Привязка — `GET /api/me/messengers` и `POST /api/me/messengers/:provider/link`
  плюс боты (`POST /api/messengers/telegram/webhook` и `/max/webhook` с секретом); в кабинетах
  клиента и мастера висит плашка «Привяжите Telegram или Max, чтобы бесплатно получать
  напоминания», прячется она только когда канал есть;
- отзывы идут полным циклом: клиент оставляет отзыв по завершённому визиту из «Моего профиля»
  (`POST /api/reviews` — только по своей записи и один раз, `GET /api/reviews/mine`), мастер
  видит его в кабинете, отвечает клиенту (`POST /api/cabinet/reviews/:id/reply`), а публикует
  или скрывает **администратор** в разделе `/admin/reviews` — мастер на статус не влияет,
  иначе негатив можно было бы просто не публиковать. Рейтинг и число отзывов мастера
  пересчитываются по опубликованным, поэтому карточка мастера и витрина `/reviews`
  (публичный `GET /api/reviews`) всегда показывают актуальные оценки и ответы мастеров;
- «Горящие окна» — не демо-офферы: `GET /api/last-minute` собирает ближайшие свободные окна
  мастеров из расписаний и занятых записей (те же правила, что при записи), с фильтром по
  региону и периоду; из карточки витрины клиент попадает в форму записи с уже выбранными
  мастером, услугой и временем. Каталог с `?windows=1` отдаёт карточкам настоящие окна —
  и на странице поиска, и в карточке мастера вместо демо-времени;
- форма записи показывает живые даты (14 дней от сегодня), а не демо-неделю из макета;
- избранное живёт в базе: клиент отмечает мастера сердечком на главной, в поиске и на
  карточке (`POST /api/favorites`), видит свой список на `/favorites` с ближайшим свободным
  окном (`GET /api/favorites`) и убирает мастера тем же сердечком. Избранное чужому не видно,
  повторное добавление не создаёт дубль. Когда у мастера освобождается окно — кто-то отменил,
  перенёс запись или мастер открыл рабочий день, — избранные клиенты получают уведомление
  «освободилось окно» (не чаще одного раза в 6 часов, и без тех, у кого уже есть запись);
- «Статистика», «Клиенты», «Продвижение» и главная кабинета считают цифры по базе:
  выручка, средний чек, топ услуг, статусы, источники записей, динамика по дням и база
  клиентов с визитами и чеками. Рекламных метрик (показы, клики, расходы) в системе нет —
  такие блоки помечены на экране как демонстрационные до подключения рекламных кабинетов;
- таблица «Записи» показывает реальные данные из базы (строки макета остаются только
  как запасной вариант, если API недоступен), счётчики вкладок считаются по этим же данным;
- переписка клиента с мастером живёт в базе (`/messages`): диалог заводится с карточки мастера
  или из кабинета, сообщение второй стороне приходит в ленту уведомлений, непрочитанные считаются
  по собеседнику и видны значком в кабинете; внешних каналов (SMS/WhatsApp/Instagram) нет;
- статистика кабинета считается по записям: воронка «записи → подтверждённые → завершённые»,
  динамика за 12 месяцев, топ услуг, источники записей — без демо-чисел;
- настройки сохраняются в базу: профиль (`PATCH /api/cabinet/profile`) и часы работы
  (`PUT /api/cabinet/hours`). Выходной день закрывает запись: клиент не видит окон,
  а попытка записаться получает 409 `day_off`;
- сессия не обрывается: access-токен живёт 15 минут, refresh — месяц.
  `POST /api/auth/refresh` продлевает пару с ротацией (старый refresh перестаёт работать),
  сессии хранятся по устройству (`sessions`), `POST /api/auth/logout` отзывает свою сессию,
  а клиент сам продлевает доступ при первом 401 — пользователь не вводит код заново;
- вход и регистрация — разные экраны. На `/login` сначала выбирают, **куда входят** —
  «клиент» или «мастер», — затем телефон и код: незарегистрированный номер получает
  `404 not_registered` и предложение создать аккаунт, а попытка войти не в свой кабинет —
  `403 role_mismatch` (клиент не попадёт в кабинет мастера и наоборот). На `/register`
  выбирают, **кем регистрируются**: «я мастер» сразу создаёт профиль мастера и открывает
  кабинет, «я клиент» — личный кабинет; занятый номер получает `409 already_registered`
  с переходом на вход. Администратор входит через отдельную форму `/admin/login` — только
  вход, без выбора роли и регистрации (и на сайте на неё нет ссылок). После входа клиент
  попадает в «Мой профиль», мастер — в `/pro`, администратор — в модерацию;
- настройки клиента живут в базе (`/settings`): имя (`PATCH /api/client/profile`) сохраняется
  и видно мастеру в записях, а переключатели уведомлений честно глушат события — выключенные
  «уведомления о записи» не приносят ни подтверждения, ни отмены, ни завершения, выключенные
  «акции и свободные окна» — предложений об освободившемся окне. Удаление аккаунта
  (`DELETE /api/client/account`, подтверждение словом «УДАЛИТЬ») отменяет будущие визиты,
  оставляет мастеру обезличенную историю, а избранное, уведомления и переписку удаляет;
- на главной и на странице «Карта мастеров» есть выбор города: Санкт-Петербург или
  Ленинградская область. Выбор запоминается и фильтрует каталог, а мастера выбранного
  региона показываются на карте города. Карта — Яндекс: с ключом `VITE_YANDEX_MAPS_KEY`
  рисуются метки мастеров, без ключа открывается виджет Яндекса и список мастеров рядом;
- мастер загружает фото: `/pro/media` — аватар, работы и сертификаты (`POST /api/cabinet/media`,
  multipart: `file`, `kind`, `caption`). Принимаем только изображения до 5 МБ (`400 bad_type`
  и `413 too_large` на остальное), sharp делает два варианта — `web` 1200 px и `thumb` 320 px,
  файлы лежат в `MEDIA_DIR`, в базе — метаданные (`master_media`). Аватар один (новый вытесняет
  старый), работы показываются лентой на странице мастера и в каталоге вместо инициалов;
- витрина знает географию: справочник `locations` — 72 станции метро Санкт-Петербурга
  (с линиями и цветами) и 18 городов области. Мастер привязан к станции или городу
  (`masters.metro_slug` / `district_slug`), витрина фильтруется (`GET /api/masters?metro=…`,
  `?district=…`), а фильтр на карте показывает только те места, где есть мастера
  (`GET /api/locations/popular`);
- демо-данные пересоздаются из кабинета: `POST /api/cabinet/demo/reset` (только dev).

- сообщения клиентам уходят через очередь (`deliveries`): канал выбирается в админке
  (`/admin/deliveries`) — `auto` идёт по привязке (Telegram → Max → журнал системы),
  `log` пишет в журнал (стенд), `webhook` шлёт POST на свой адрес. Напоминание о визите
  ставится за сутки; перенос и отмена снимают старое и ставят новое; сбой провайдера не теряет
  сообщение — оно возвращается в очередь с паузой, до трёх попыток, и повторяется кнопкой;
- предоплата: мастер задаёт процент по услуге (в кабинете, «Услуги»), сумма фиксируется в момент
  записи и видна клиенту ещё до записи. Запись ждёт оплату и подтверждается сама, когда деньги
  пришли. Деньги принимает мастер (`manual`: перевод/наличные, клиент жмёт «Я оплатил(а)»,
  мастер — «Деньги пришли») или платёжный шлюз (`webhook`: мы отправляем операцию и получаем
  ссылку на оплату, шлюз сообщает об оплате вебхуком `POST /api/payments/webhook`). Страница
  оплаты — `/pay/:bookingId`, отмена оплаченной записи возвращает предоплату. Раздел админки
  `/admin/payments` показывает сводку и позволяет подтвердить или вернуть деньги;

## Демо-доступы

| Роль | Телефон | Что видно |
| --- | --- | --- |
| Мастер (владелица кабинета) | `+7 999 000-00-01` | кабинет `/pro` целиком |
| Администратор | `+7 999 000-00-09` | модерация отзывов `/admin/reviews` |
| Клиент | любой новый номер | запись, «Мой профиль», отмена |

Вход и регистрация разведены: `/login` — вход (выбор кабинета: клиент или мастер), `/register` —
создание аккаунта с выбором роли. Администратор входит через `/admin/login` — отдельную форму
без ссылок на сайте.

Код подтверждения в dev-режиме возвращает сам API (`OTP_DELIVERY=response`, он же
по умолчанию при `DEV_OTP_ENABLED=true`) и подставляется в форму автоматически. Кнопки
«в один клик» работают без ключей: кнопка рисуется выключенной, а ручка отвечает `503`
(так же ведут себя Telegram и Max без токенов ботов). Чтобы включить провайдера,
заполните `YANDEX_*` / `VK_*` / `TELEGRAM_*` / `MAX_*` в `apps/api/.env` — подробности
в комментариях к `.env.example` и в [DEPLOY.md](./DEPLOY.md).

## Проверки

```bash
npx tsc --noEmit                  # типы фронтенда
npm run build                     # сборка фронтенда
cd apps/api && npm run build      # типы и сборка API

# сквозные проверки без браузера (нужен запущенный Vite + API)
cd tools/devcheck && npm install
npm run bundle                    # собрать приложение в bundle.js
npm run routes                    # отрисовать все маршруты (кабинет — под сессией мастера)
npm run e2e                       # сценарий «мастер создаёт запись → завершает → клиент видит и отменяет»
npm run data                      # цифры разделов и витрины совпадают с ответами API
npm run messages                  # переписка: диалоги, непрочитанные, отправка в обе стороны
npm run stats                     # воронка и динамика из базы, сохранение профиля и часов работы
npm run session                   # продление сессии, ротация refresh, выход и автопродление в клиенте
npm run reviews                   # отзыв по завершённому визиту, модерация, ответ мастера, рейтинг
npm run reschedule                # перенос записи клиентом и мастером, проверки слота
npm run roles                     # выбор роли при входе, свои кабинеты, доступ в админку
npm run city                      # города, фильтр каталога и карта выбранного региона
npm run services                  # CRUD услуг мастера, чужие услуги, удаление записи на услугу
npm run favorites                 # избранное в базе, сердечки, уведомление об окне и антиспам
npm run last-minute               # горящие окна из расписаний: занятие, отмена, фильтры
npm run settings-client           # профиль, настройки уведомлений и удаление аккаунта клиента
npm run deliveries                # очередь доставки: канал, напоминания, повтор после сбоя
npm run payments                  # предоплата: процент в прайсе, шлюз, подтверждение, возврат
npm run past-slot                 # прошедшие окна, лид-тайм, пояс и шаг сетки мастера
npm run no-show                   # неявки, поздние отмены, чёрный список, история записи
npm run scheduler                 # авто-отмена заявок и авто-закрытие визитов
npm run otp-limits                # хеш кодов, лимиты отправки и ввода, настройки админки
npm run locations                 # справочник метро и ЛО, фильтр витрины, выбор места на карте
npm run oauth                     # способы входа, identities, телефон как контакт
npm run messengers                # вход через ботов Telegram и Max, привязка канала, плашка
npm run media                     # загрузка фото, ресайз, лимиты, аватар на витрине
npm run admin                     # админка: доступы, мастера, отзывы, лимиты входа
```

## Переменные окружения

- фронтенд: `VITE_API_URL`, `VITE_API_TARGET`, `VITE_ALLOWED_HOSTS`;
- API: см. `apps/api/.env.example` (порт, секреты JWT, TTL кода, шаг слотов, рабочие часы,
  приём кода `OTP_DELIVERY`, доставка сообщений `DELIVERY_*`, предоплата `PAYMENT_*`,
  вход через внешние сервисы `YANDEX_*` / `VK_*` / `PUBLIC_WEB_URL` / `OAUTH_REDIRECT_BASE`,
  боты `TELEGRAM_*` / `MAX_*` / `BOT_LOGIN_TTL_MINUTES`, медиа `MEDIA_*`).

Документы проекта: [docs/STATUS.md](./docs/STATUS.md) — что сделано и карта работ,
[docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md) — разбор архитектурных вопросов (БД, время,
статусы, доступы, деньги) и план доработок, [DEPLOY.md](./DEPLOY.md) — развёртывание.

Прод собирается как три контейнера — сайт (`Dockerfile.web`: сборка Vite + Caddy),
API (`apps/api/Dockerfile`) и Postgres; серверный образ работает на драйвере `pg`,
локальный WASM-драйвер PGlite в него не попадает. Миграции API накатывает при старте,
так что отдельного шага с миграциями в деплое нет. Подробности — в [DEPLOY.md](./DEPLOY.md).
