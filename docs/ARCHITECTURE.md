## Блок 1. База данных и сущности

### 1. Связь «Мастер — Салон — Рабочее место»

**Сейчас.** Таблиц салонов и рабочих мест нет. `masters` (`apps/api/src/db/schema.ts`) —
самостоятельная сущность, и адрес места приёма лежит прямо в ней: `metro`, `address`,
`city`, `region`, `lat`, `lng`. Запись не знает, *где* она состоится: адрес подставляется
в ответ из карточки мастера (`serializeBooking` → `address: master.address ?? master.metro`).

Следствия: один мастер = один профиль = один адрес; работать в двух салонах в разные дни
нельзя; совмещать «на дому» и «в салоне» нельзя; расписание (`working_hours`) и занятость
(`bookings`) считаются по мастеру целиком, без места.

**План** (этап 3, после решения продукта).

1. Решить: нужны ли настоящие салоны на текущем этапе. Пока маркетплейс для частных
   мастеров СПб + ЛО, вариант «мастер = место» рабочий. Салоны — когда появляются
   студии с несколькими мастерами и арендой.
2. Миграция `0013_salons.sql`: `salons` (id, name, address, metro, city, region, lat, lng,
   phone, timezone, owner_user_id, active) и `workspaces` (id, salon_id, master_id, title,
   `kind: chair|room`, active, unique(salon_id, master_id)) — «рабочее место», в котором
   мастер принимает.
3. Миграция данных: каждому текущему мастеру создать салон из его `address/metro/...`
   и один workspace (salon_id = этот салон). Так старые данные остаются валидными.
4. `bookings.workspace_id` (после бэкфилла — NOT NULL) и `bookings.location_kind`
   (`salon|home|customer_place`).
5. Расписание и занятость — по месту: `working_hours.workspace_id`, `freeSlotsForDay` /
   `assertSlotFree` принимают workspaceId. Один мастер в разных местах получает разные
   расписания, и занятость в салоне А не блокирует окна в салоне Б.
6. «На дому» — виртуальное место: `masters.home_visit boolean`, `masters.home_radius_km`,
   адрес клиента в записи (см. вопрос 2). Запись с `location_kind = customer_place`
   требует адрес и проверяет радиус (409 `out_of_radius`).
7. Кабинет: раздел «Места работы» (`/pro/places`) — подключиться к салону, часы по
   каждому месту, переключатель места в расписании. Публичная карточка мастера — список
   мест с картой.
8. Проверки: новый набор `places.mjs` — два места с разными расписаниями, занятость не
   смешивается, выезд за пределы радиуса отклоняется.

### 3. Модель услуг: общий каталог или у каждого мастера

**Сейчас.** Услуга жёстко привязана к мастеру: `services.master_id NOT NULL`,
у четырёх мастеров в сиде 40 независимых строк. Цена, длительность и процент
предоплаты — у мастера. `category` — просто строка, общего каталога и категорий
как сущностей нет. Витрина отдаёт плоский список (`GET /api/services?master=slug`),
агрегации «кто делает услугу X и от какой цены» нет.

**План** (этап 3).

1. Миграция: `service_categories` (id, slug, name, sort) и `service_catalog`

2. `services.catalog_id` (nullable FK на переходный период): услуга мастера — либо

3. Миграция данных: сгруппировать текущие услуги по (category, name), создать записи

   с четырьмя вариантами цен.
4. Кабинет: создание услуги из каталога (поиск + подстановка длительности/цены) или

5. Публично: `GET /api/service-catalog` (категории → услуги, у каждой `priceFrom`,
   `priceTo`, `mastersCount`, `durationMinutes`), фильтр каталога `?catalogId=`,
   сортировка по цене/популярности.
6. Проверки: `catalog-services.mjs` — агрегаты сходятся, «Маникюр классический» у 4
   мастеров с разными ценами, фильтр «услуга → мастера, которые её делают».

### 4. Модель отзывов

**Сейчас — сделано.** `reviews.booking_id` (FK на `bookings`, `ON DELETE SET NULL`,
nullable только для исторических записей из сидов) + уникальный индекс
`reviews_booking`: одна запись — один отзыв. Оставить отзыв можно только по **своей**
завершённой записи: 403 на чужую, 409 `not_completed` и `already_reviewed`
(`apps/api/src/routes/reviews.ts`). Ответ мастера — `reply_text` + `replied_at`
(одна реплика, пустая строка убирает ответ). Модерация — только администратор:
`POST /api/admin/reviews/:id/moderate`, статусы `published|moderation|hidden`.
После публикации рейтинг и число отзывов пересчитываются (`recalcMasterRating`).

**Что дописать** (небольшой объём).

1. В публичной выдаче явно помечать отзывы «подтверждён визитом» (`booking_id != null`)
   и не показывать бейдж у исторических.
2. `reviews.moderated_by`, `moderated_at`, `hidden_reason` — чтобы решение админа было
   объяснимо (жалоба мастера, спам, мат).
3. Жалоба на отзыв: `review_reports` (review_id, author, reason, status) + ручка
   для мастера/клиента и разбор в админке.
4. Фото в отзывах — после пункта 2 (та же `master_media`, `kind: review`).
5. Решить правило авто-публикации: сейчас всё уходит в `moderation`, у сидов
   `published`. Вариант: авто-публикация без жалоб, ручная проверка — по жалобе.

## Блок 2. Время, календарь и бронирование

### 5. Шаг сетки и длительность

**Сейчас.** `SLOT_STEP_MINUTES=30` (env, `env.slotStepMinutes`). Длительность — своя у
каждой услуги (5…600 мин в кабинете). `freeSlots` (`apps/api/src/lib/time.ts`) идёт от
начала рабочего дня с шагом step и берёт только **полные** окна: `start + duration <=
working.end` и нет пересечения с занятыми. Занятость — из `bookings` со статусом ≠ cancelled.

Что это значит на практике:

- одна запись = одна услуга; «Снятие + Маникюр + Гель-лак» (2 ч 15 мин) как одна запись
  невозможен — комбо-услуг нет;
- если свободны только «дыры» по 1,5 ч, услуга на 2 ч 15 мин **не предлагается вообще**:
  склейки окон и частичных вариантов нет;
- записаться в прошлое не мешает ничто: `freeSlotsForDay` отдаёт слоты и на прошедшие
  даты, проверки «слот раньше сейчас + N минут» в `assertSlotFree` нет.

**План.**

1. Мастеру — свой шаг сетки: `masters.slot_step_minutes` (15/30/60) с фолбэком на env,
   переключатель в настройках кабинета.
2. Комбо-услуги: `booking_services` (booking_id, service_id, price, duration) — запись
   получает список услуг. Проверки: все услуги принадлежат мастеру и активны, длительность
   и цена — суммы, предоплата — по правилам каждой услуги (или общий процент — решить).
3. Слоты для комбо: `freeSlotsForDay(masterId, суммарнаяДлительность)` (уже умеет любую
   длительность) + UI с мультивыбором услуг и итогом по времени и деньгам.
4. Запрет прошлого и «минимальный запас»: env `BOOKING_MIN_LEAD_MINUTES=60`;
   `freeSlotsForDay` не отдаёт слоты раньше `now + lead`, `assertSlotFree` отвечает
   409 `past_slot`. Это правка на существующий баг, её стоит сделать вне очереди.
5. Нечётные длительности (135 мин при шаге 30): сетка от начала дня уже даёт варианты,
   но последнее окно дня окажется неиспользованным — добавить вариант «прижат к концу
   рабочего дня» (`start = end − duration`, если это не ломает соседние записи).
6. Проверки: расширить `services.mjs` + новый `bundles.mjs` — комбо 135 мин, склейка,
   отказ в прошлом.

### 6. График работы

**Сейчас.** `working_hours(master_id, weekday 0…6, start_minute, end_minute)` с уникальным
индексом `(master_id, weekday)` — одно окно на день недели. Нет строки на weekday → выходной.
Если строк нет вообще (новый мастер) — работают значения по умолчанию из env, иначе новый
кабинет нельзя было бы записать (`apps/api/src/lib/schedule.ts`). Кабинет правит неделю
через `GET/PUT /api/cabinet/hours`.

Чего нет: исключений на конкретную дату (отпуск, больничный, «работаю в свой выходной»),
нескольких интервалов в день (утро + вечер), циклических смен (2/2, 3/3), массовых правок
(«скопировать неделю», «сделать выходной на период»). Смена 2/2 невыразима: один и тот же
weekday повторяется каждую неделю.

**План.**

1. Миграция: `day_schedule` (master_id, `date` date, start_minute, end_minute,
   `kind: work|off`, note, unique(master_id, date)) — исключения на дату;
   `PUT /api/cabinet/schedule/:date`, `DELETE` — вернуть недельное правило.
2. Снять `unique(master_id, weekday)` в `working_hours`, добавить `slot_index` —
   несколько интервалов в день (обед, вторая смена); `scheduleForDay` возвращает
   **список** интервалов, `freeSlotsForDay` считает по каждому (слоты не «перетекают»
   через обед).
3. Шаблоны смен: `shift_templates` (master_id, name, cycle_days, pattern jsonb) +
   `POST /api/cabinet/schedule/apply-template` (сгенерировать даты на N недель вперёд) —
   так появляются 2/2 и «заполнить неделю вперёд».
4. Кабинет: календарь расписания (неделя/месяц) с действиями «выходной», «копировать
   прошлую неделю», «применить шаблон», «особые часы на дату».
5. Проверки: `schedule2.mjs` — 2/2, отпуск, два интервала, влияние на слоты и горящие окна.

### 7. Технические перерывы и блокировки времени

**Сейчас — нет.** Занятость считается только по `bookings` (кроме cancelled). Мастер не
может заблокировать обед, личные дела или запись, принятую по телефону мимо приложения —
такое время останется «свободным» и клиент займёт его.

**План** (этап 2, небольшой объём — высокая ценность).

1. Таблица `time_blocks` (id, master_id, workspace_id?, start_at, end_at,
   `kind: break|personal|offline_booking|other`, title, created_by, created_at).
2. CRUD: `GET /api/cabinet/blocks?from&to`, `POST /api/cabinet/blocks`,
   `DELETE /api/cabinet/blocks/:id`; при пересечении с существующей записью — 409
   `block_overlaps_booking` (или согласованный перенос).
3. Все расчёты занятости — общие: `freeSlotsForDay`, `assertSlotFree`, `last-minute`,
   `favorites` (окно у избранного) учитывают блоки тем же `busy`-списком.
4. Быстрая запись «клиент по телефону»: `POST /api/cabinet/bookings` уже есть
   (`source=master`, статус confirmed) — вывести в UI одной кнопкой «Занять время»,
   а блок использовать для «просто занято».
5. Проверки: `blocks.mjs` — блок скрывает слот, отмена блока возвращает, пересечение
   с записью отклоняется, блок виден в расписании.

### 8. Часовые пояса

**Сейчас.** Хранение правильное: все моменты — `timestamp with time zone` (на диске UTC).
Но бизнес-логика считает «минуты дня» в **локальном поясе процесса**: `parseISODate`
(`new Date(y, m, d)`), `minutesOfDay` (`getHours`), `weekdayIndex` (`getDay`) в
`apps/api/src/lib/time.ts`. При этом тексты сообщений берут **UTC**:
`whenLabel` в `lib/notify.ts` и `whenText` в `lib/delivery/reminders.ts` используют
`getUTCHours`, а `toISODate` рядом — локальную дату. В sandbox `TZ=UTC`, в прод-стеке
`TZ: Europe/Moscow` (`docker-compose.yml`) — то есть в проде время визита в SMS
разойдётся с интерфейсом на 3 часа. Плюс у мастера нет поля таймзоны: вся площадка
живёт в одном поясе, а «сегодня» и «горящие окна» зависят от часов сервера.

**План** (этап 1 — это исправление, а не фича).

1. `masters.timezone` (IANA, default `Europe/Moscow`) и справочник «город → пояс»
   (позже `salons.timezone` из вопроса 1).
2. Переписать `lib/time.ts` на tz-aware функции через `Intl.DateTimeFormat`: `dayBounds(dateISO, tz)`,
   `minutesOfDay(date, tz)`, `fromMinutes(dateISO, minutes, tz)`, `weekdayIndex(date, tz)`,
   `nowIn(tz)`. Запретить `getHours|getUTCHours|setHours|getDay` вне этого модуля
   (проверка в CI грепом или ESLint-правилом).
3. Перевести на них все места: слоты, расписание, `last-minute`, избранное, тексты
   уведомлений и напоминаний, статистику кабинета, страницу оплаты.
4. API: в `serializeBooking` добавить `timezone` мастера и `utcOffsetMinutes` — фронт
   показывает время визита в поясе мастера и, если пояс клиента другой, подписывает
   «по вашему времени 12:00».
5. Проверки: devcheck прогонять дважды — `TZ=UTC` и `TZ=Europe/Moscow` — и добавить
   кейс визита на границе суток (например, 00:30 по Москве).

## Блок 3. Жизненный цикл записи

### 9. Статусы записи

**Сейчас.** `bookings.status` — `pending | confirmed | completed | cancelled`, плюс
`payment_status` (`none|pending|paid|refunded`) и `source` (`client|master`). Переходы
не валидируются: `confirm`/`complete`/`cancel` в кабинете просто пишут новый статус
(`apps/api/src/routes/cabinet.ts`), перенос блокирует только cancelled/completed.
Кто и почему отменил — в строке не хранится (только текст в уведомлениях); «клиент не
пришёл» статуса нет; истории изменений нет; `updated_at` нет.

**План.**

1. Миграция: `bookings.cancelled_by` (`client|master|system`), `cancelled_at`,
   `cancellation_reason`, `updated_at`; «не пришёл» — отдельный статус `no_show`
   (или флаг `attendance`, решить; рекомендуемый набор: pending → confirmed →
   completed | no_show | cancelled).
2. `booking_events` (booking_id, from_status, to_status, by_user_id, role, reason, created_at) —
   append-only журнал: нужен для споров «кто отменил» и для аналитики.
3. Единый автомат `applyBookingStatus(booking, next, actor)` в `lib/booking-status.ts`
   с таблицей разрешённых переходов (409 `bad_transition`); заменить прямые `db.update`
   в `routes/cabinet.ts` и `routes/bookings.ts`.
4. Политика денег в переходах: отмена мастером → возврат предоплаты (есть), `no_show` →
   предоплата не возвращается (решить), отмена системой по дедлайну → возврат.
5. Фронт: кнопка «Клиент не пришёл» (доступна после времени визита), в карточке записи —
   история статусов.
6. Проверки: `lifecycle.mjs` — все переходы, запрет повторов, no_show, история.

### 10. Логика отмены: авто-отмена, дедлайны, штрафы

**Сейчас — ничего из этого нет.** Заявка `pending` висит бесконечно: мастер не обязан
подтверждать, система не отменяет. Клиент может отменить в любой момент, в том числе
за минуту до визита — предоплата при этом возвращается полностью. Прошедшие визиты
не закрываются сами: пока мастер не нажмёт «Завершить», запись остаётся `confirmed`
и портит статистику. Напомнить о визите — напомним (за 24 ч), но «если не подтвердишь —
сгорит» не бывает.

**План.**

1. Env-политика: `BOOKING_CONFIRM_DEADLINE_MINUTES=120`,
   `BOOKING_AUTOCOMPLETE_HOURS=24`, `BOOKING_MIN_LEAD_MINUTES=60` (см. вопрос 5).
   Онлайн-отмена клиента фиксирована на правило «строго больше 6 часов» и не настраивается env-переменной.
2. Планировщик (расширить существующий воркер доставки — он уже крутится каждые 30 с):
   - авто-отмена неподтверждённых `pending` старше дедлайна (уведомление обеим сторонам,
     возврат предоплаты, `cancelled_by=system`);
   - авто-закрытие визитов, начавшихся ≥ N часов назад: `completed`, если мастер отметил
     визит, иначе `no_show` (или `completed` по умолчанию — решить);
   - предупреждение клиенту «до визита 2 часа, предоплата не внесена» (см. вопрос 11).
3. Дедлайн онлайн-отмены: `booking.cancelFreeUntil` вычисляется от `startAt − 6 часов`
   и отдаётся в API. За 6 часов и менее отмена блокируется сервером; клиенту предлагается
   связаться с мастером. Платные SMS не используются.
4. `POST /bookings/:id/cancel` — писать `cancelled_by`, причину и запускать возврат
   (возврат уже есть, остальное — из вопроса 9).
5. Проверки: `lifecycle.mjs` с крошечными значениями env в дев-режиме (например,
   дедлайн 1 минута) — заявка действительно сгорает, визит закрывается сам.

### 11. Триггеры уведомлений и планировщик

**Сейчас — в основном сделано.** Точки событий: `notifyBookingEvent` (создание, подтверждение,
перенос, отмена, завершение), `review_replied`, `favorite_slot` (окно у избранного),
OTP. Доставка — очередь `deliveries` с `log|webhook` и привязанными бесплатными ботами,
повторы с паузой (до 3 попыток), админка очереди, ручной повтор. Платные SMS-транспорты
не используются. Напоминание ставится не «проверкой раз
в час», а строкой очереди с временем отправки (`scheduledFor = startAt − 24 ч`, но не
раньше «сейчас»); перенос и отмена снимают старое и ставят новое. Планировщик — свой
воркер в процессе API: первый прогон через 1 с, далее каждые `DELIVERY_INTERVAL_SECONDS=30`
(`apps/api/src/server.ts`). Cron/Celery не нужны: очередь в БД делает то же самое.

**Что дописать.**

1. Напоминание не одно, а два: `REMINDER_LEAD_MINUTES=1440,120` — за сутки и за 2 часа.
2. Триггеры из вопроса 10: «заявка не подтверждена», «предоплата не внесена за N часов»,
   «мастер не завершил визит вчера» (мастеру).
3. Многопроцессность: сейчас при двух инстансах API воркеры продублируют отправку.
   Нужен либо единственный воркер (`node dist/worker.js`), либо распределённый лок
   (`pg_advisory_lock`), либо `SELECT … FOR UPDATE SKIP LOCKED` (для Postgres — самый
   честный вариант, PGlite его не умеет, поэтому в dev оставить последовательный воркер).
4. Шаблоны сообщений в БД (`message_templates(kind, channel, locale, body, version)`) —
   сейчас тексты собираются строками в коде; шаблоны дадут правки без деплоя.
5. Метрики доставки: доля `failed`, лаг очереди, ручка `/api/admin/deliveries/stats` и
   предупреждение в админке при систематических сбоях.
6. Проверки: дополнить `deliveries.mjs` — два напоминания, авто-отмена, порядок сообщений.

## Блок 4. Безопасность, роли и API

### 12. Разграничение прав (RBAC)

**Сейчас — есть, но «по месту».** Три middleware в `apps/api/src/lib/auth.ts`:
`requireAuth` (проверяет access-токен и подкладывает `currentUser` с ролью и `masterSlug`),
`requireAdmin`, `requireMaster`. Дальше — построчные проверки владения:
`GET /api/bookings` берёт телефон из токена и отдаёт 403 на чужой `phone`;
`/api/payments/*` — функция `accessTo` (владелец записи / её мастер / админ);
кабинет (`/api/cabinet/*`) — только по `masterSlug` из сессии, чужие услуги 403,
чужая запись 404; модерация и деньги — только админ (мастер получает 403).
Это покрыто проверками (`roles`, `favorites`, `payments`, `services`), но:

- проверки размазаны по ручкам — нет одного места, где видно политику;
- нет аудит-лога действий админа и денежных операций;
- нет rate-limit (см. вопрос 13), нет матрицы «ручка × роль × чужой объект» в тестах.

**План.**

1. `lib/access.ts`: `canViewBooking(user, booking)`, `canManageMaster(user, masterId)`,
   `canModerateReviews(user)`, `canViewPayments(user)` и хелпер `denyForbidden(reply)`;
   постепенный перевод ручек, для чужих сущностей — 404 вместо 403 (не раскрывать факт
   существования).
2. `audit_log` (actor_user_id, actor_role, action, entity, entity_id, payload jsonb, ip,
   created_at) — писать для модерации, денег, изменений профиля мастера и прав; ручка
   `/api/admin/audit`.
3. Матрица доступа в `tools/devcheck`: таблица ручек → в цикле проверяются гость/клиент/
   чужой клиент/мастер/чужой мастер/админ. Это разом закрывает и текущие пробелы в тестах.
4. Ревизия персональных данных: мастеру в ответах — телефон клиента (для связи) и имя,
   но не история покупок чужих клиентов; админу — всё, но с записью в аудит.

### 13. Аутентификация

**Сейчас.** Вход только по телефону + OTP: `POST /auth/request-otp` (код 6 цифр, TTL 300 с),
`POST /auth/verify-otp` (режимы `login|register|auto`, роли `client|master|admin`,
`admin_registration_disabled` и т.п.). Выдаются JWT: access 15 минут, refresh 30 дней;
refresh хранится хешем (sha256) в `sessions` с `sid`+`jti` и ротацией при продлении;
выход удаляет сессию; `GET /auth/me`. Соцсетей, СБП, пароля, 2FA, лимитов — нет.
Код OTP лежит в БД **в открытом виде**, попытки ввода не считаются.

**План.**

1. Пункт 11 карты (защита): `@fastify/rate-limit` — лимит по IP и по номеру
   (например, 3 запроса кода за 15 минут, 5 неверных вводов → блок 15 минут);
   хранить код как `sha256(code + pepper)`; новый запрос гасит прежние коды;
   задержка/капча при переборе.
2. `identities` (id, user_id, `provider: vk|yandex|google`, external_id, meta jsonb,
   unique(provider, external_id), created_at) — вход через соцсети с привязкой к
   существующему аккаунту по телефону/почте.
3. 2FA для админа — обязательна: `users.totp_secret`, `totp_enabled`, экран настройки.
   Сейчас админ входит тем же кодом из SMS, что и клиент.
4. Опционально: e-mail + пароль как резервный вход для мастеров (argon2), сброс по ссылке.
5. Управление сессиями: `GET /auth/sessions` (устройства, последняя активность),
   `DELETE /auth/sessions/:id`, «выйти везде» — модель `sessions` уже готова.
6. Про СБП: это способ оплаты, а не вход. У нас уже есть `payment.provider=webhook` —
   СБП подключается на стороне шлюза (см. вопрос 15), отдельной интеграции не требуется.
7. Проверки: `auth-limits.mjs` — лимиты, блокировка, «старый код не работает».

### 14. Пагинация и фильтрация

**Сейчас.** `GET /api/masters` — фильтры `query` (имя/теги/метро), `service` (по тегам,
не по услугам), `region`, `windows=1` (считать ближайшие окна), сортировка по рейтингу;
пагинации нет — отдаётся весь список. `GET /api/services?master=` — весь прайс.
`GET /api/last-minute` — `region`, `days`, `limit`, `perMaster` (есть). Админские
`/admin/deliveries` и `/admin/payments` — параметр `limit` без курсора.
`/api/bookings`, `/api/cabinet/bookings`, `/api/cabinet/clients`, `/api/cabinet/reviews` —
полные списки. Фильтров по цене, рейтингу, расстоянию и свободной дате нет;
гео-поиск — только «город/регион».

**План.**

1. Единый конверт списков: `{ items, total, nextCursor }`; `limit` (1…100) + курсор
   `(sort_key, id)` — для публичных лент, offset — для админских таблиц.
2. `/api/masters`: `priceFromMax`, `priceTo`, `ratingMin`, `metro`, `city`, `region`,
   `sort=rating|price_asc|distance|new`, `date=YYYY-MM-DD&serviceId=` (только свободные
   на дату), `radiusKm` + `lat/lng`, `home=1` (выезд, после вопроса 2).
3. Индексы: `masters(rating)`, `masters(region)`, `services(price)`, `bookings(master_id, start_at)`
   (есть), `services(catalog_id)` (после вопроса 3). Для радиуса — bounding box по
   `lat/lng` + Haversine в SQL; PostGIS в PGlite недоступен, поэтому либо ручной расчёт
   (до десятков тысяч мастеров хватает), либо переход на Postgres + PostGIS при росте.
4. Фасеты поиска: `GET /api/search/facets` — сколько мастеров попадает в диапазоны цены,
   рейтинга и по метро (чтобы фильтры в UI показывали числа).
5. Фронт: «Показать ещё»/бесконечная лента, фильтры в URL (шарится ссылкой), скелетоны.
6. Проверки: `search.mjs` — курсор не дублирует и не теряет записи, фильтры сходятся
   с ручным подсчётом, «свободно на дату» совпадает со слотами мастера.

## Блок 5. Финансы и монетизация

### 15. Тип транзакций: эквайринг или агрегатор

**Сейчас — «предоплата + оплата на месте».** Реализовано (пункт 9 карты):
`payments` (booking_id, amount, provider, status, externalId, payUrl, paidAt, refundedAt)
и процент предоплаты в услуге. Два режима приёма (`payment.provider` в админке или env):

- `manual` — деньги принимает мастер (перевод/наличные): клиент жмёт «Я оплатил(а)»,
  мастер подтверждает поступление в кабинете;
- `webhook` — платёжный шлюз: мы отправляем операцию, получаем ссылку на оплату,
  шлюз сообщает об оплате вебхуком `POST /api/payments/webhook` (с секретом).

Остаток стоимости клиент отдаёт мастеру на месте. Комиссии маркетплейса нет: деньги
платформу не проходят (при `manual` — вообще сразу мастеру), у нас только факт операции.
Возврат при отмене — полный, автоматический.

**План.** Это продуктовое решение, развилка:

- **A. Агрегатор (оставить как есть).** Платформа продаёт записи, а не платежи: эквайринг
  только для предоплаты, чтобы снизить неявки. Дописать: отчёт мастеру
  (`/pro/finance`: получено предоплат, возвращено, ждём оплату), выгрузка реестра,
  фискальные чеки — на стороне шлюза. Монетизация — подписка/продвижение/лиды,
  а не комиссия с оборота.
- **B. Маркетплейс с комиссией.** Нужен договор эквайринга (ЮKassa, CloudPayments,
  Т-Банк; split-платежи или отдельный счёт платформы) и выплаты мастерам. Тогда —
  вопрос 16.

Рекомендация: сейчас закрепить A, но сразу заложить в схему поля под B (их добавление
на пустой таблице `payments` ничего не ломает).

### 16. Баланс, комиссия и холдирование

**Сейчас — нет ничего из этого.** Нет комиссии, нет баланса мастера, нет холдирования,
нет выплат. Есть только операции предоплаты по записи и полный возврат при отмене —
то есть деньгами платформа не управляет и обязательств перед пользователями не несёт.

**План** (только если выбран вариант B).

1. `payments` += `commissionAmount`, `providerFee`, `netAmount`, `captureStatus`
   (`authorized|captured|released`), `payoutId`.
2. `ledger_entries` — двойная запись: (id, account `master:<id>|platform:fees|client:<phone>`,
   direction, amount, currency, ref_type, ref_id, created_at), строки только добавляются;
   `master_balances` (master_id, available, pending, updated_at) — материализованный итог
   из проводок (пересчитывается периодически или триггером).
3. Холдирование: `authorized` при записи → `captured` после `completed` (или авто-закрытия
   из вопроса 10) → `released`/`refunded` при отмене. Политика `no_show` — решить
   (удержание части предоплаты = доход платформы/мастера).
   Пошагово безопаснее: сначала оставить текущую схему «полный платёж + возврат»
   (она уже работает и понятна клиенту), а авторизацию вводить после первых выплат.
4. `payouts` (id, master_id, period_start, period_end, amount, status
   `draft|sent|failed`, provider_ref, paid_at) + админские ручки «сформировать реестр»
   и «выплатить»; в кабинете мастера — «Финансы»: заработано, комиссия, к выплате.
5. Сверка: `GET /api/admin/payments/reconcile` — операции, у которых `external_id` есть
   у провайдера, но нет у нас/наоборот; уведомление мастеру о выплате.
6. Проверки: `finance.mjs` — комиссия считается от суммы, баланс сходится с проводками,
   холд не даёт вывести деньги до завершения, возврат разблокирует, выплата закрывает период.
